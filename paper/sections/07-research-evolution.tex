\section{Evolution of the Research Direction}

This section is intentionally chronological.  Superseded ideas remain visible
so that later design choices can be audited rather than reconstructed from
memory.

\paragraph{Phase A: prove the ECL virtual machine.}
The initial idea treated enemy ECL as the natural zkVM target.  ECL has an
explicit instruction format, registers, comparison state, call stack, program
counter, and interpreter loop, making it attractive for an opcode-constraint
prototype.

\paragraph{Phase B: recognize the open environment.}
Source inspection showed that ECL reads Player and GameManager state, shares the
global RNG, and mutates bullets, items, GUI, and scoring state.  A proof of ECL
alone could accept forged player positions or rank.  The claim was narrowed
from ``a TH06 pattern was executed'' to ``ECL executed under supplied external
inputs,'' which was judged insufficient as the main result.

\paragraph{Phase C: reframe the game as a frame transition.}
The project moved from inventing a larger VM to extracting a deterministic
gameplay kernel $S_{t+1}=F(S_t,I_t)$.  ECL became one ordered subsystem.  This
reframing also made replay inputs a natural witness serialization.

\paragraph{Phase D: distrust replay checkpoints.}
Inspection of ReplayManager revealed that each stage carries mutable resources
and RNG state that playback restores directly.  Merely proving successful
playback would allow forged resources at every boundary.  Canonical proof mode
must derive stage continuity and constrain or discard those snapshots.

\paragraph{Phase E: differential validation before ZK.}
The portable headless runner was found deterministic but not known equivalent:
it substitutes host math for x87 behavior and skips draw callbacks that can
write later-observable state.  The immediate milestone changed from circuit
construction to an exact replay differential runner against the shipped or an
exactly matched reference executable.

\paragraph{Phase F: digest first, snapshot on divergence.}
A naive full-state dump for 640 enemy bullets, 513 items, effects, enemies, and
ANM state on every frame is unnecessarily large.  The current design emits
ordered subsystem digests each frame, then reruns only the first mismatching
tick with a versioned field-level snapshot.  Stable slot identity and iteration
order are retained because allocation, collision, and RNG behavior can depend
on them.

\paragraph{Phase G: separate arithmetic fidelity from proof optimization.}
Raw floating-point bits can reveal a mismatch but do not make floating-point
execution cheap in a zkVM.  The arithmetic plan was therefore split into an
exact, integer-implemented floating-point baseline and a fixed-point candidate.
The exact lane protects the original-semantics claim and measures its real
cost.  The fixed-point lane is an optimization only if a refinement argument
preserves every claimed transition; corpus agreement alone cannot supply that
argument.  Otherwise it defines a different, explicitly named game kernel.

\paragraph{Phase H: make slicing a refinement theorem.}
Removing presentation state because sampled replays still finish was judged an
insufficient basis for a sound proof.  The kernel boundary is now required to
support a commuting one-frame diagram and a noninterference theorem for omitted
state, followed by induction over the input stream.  Lean is the intended
proof environment, but the theorem must also be bound to the actual C++
reference and zkVM guest; a proof of an unconnected handwritten model would not
close the claim.

\paragraph{Phase I: distinguish allocated memory from future-live state.}
The first real ANM projection was intentionally broad and immediately produced
a false Stage divergence from uninitialized, disabled interpolation members.
Guarding those members by the mode that can read them restored deterministic
traces.  The same audit then exposed the converse error: inactive Effect slots
retain motion values that can affect a later allocation, so active-only hashing
is too narrow.  The state boundary is now developed as an explicit queue of
owner-local overwrite-before-read and noninterference lemmas.

\paragraph{Phase J: bind arithmetic to original addresses.}
A source-level plan of ``use software IEEE-754 and x87 where required'' was too
coarse.  Static analysis found 5,980 x87 instructions in mapped game functions,
26 inline \code{fsincos} sites, 1,793 explicit stores, and 163 direct calls to
x87 helpers or wrappers.  It also found XMM-bearing CRT/D3DX code outside the
game-function ranges.  The fidelity lane therefore changed to an
address-indexed arithmetic IR whose operations retain original opcode, control
state, and store width.  Control word \code{0x027f} is now an explicit checked
profile, while its loader-established entry value and the processor-dependent
transcendental model remain open evidence obligations.

\paragraph{Phase K: test a basic-operation oracle without promoting it to a proof.}
The decoded 53-bit x87 profile suggested Berkeley SoftFloat's reduced-precision
extended operations as a candidate exact baseline.  A pinned differential
probe found no result-bit mismatch across more than ten million basic-operation
cases spanning binary32 inputs and the extended exponent range.  This narrowed
implementation risk, but also sharpened the claim boundary: SoftFloat is not a
formal proof, does not model x87 transcendental instructions, and does not by
itself bind arithmetic semantics to original instruction addresses.  The next
arithmetic milestone therefore became stores, conversions, status behavior,
and code-to-model binding rather than immediate fixed-point substitution.

\paragraph{Phase L: make exception priority part of the operation semantics.}
Extending the oracle to all six x87 exception bits immediately falsified the
first denormal rule: a subnormal dividend divided by zero set zero-divide but
not denormal-operand for the isolated arithmetic instruction.  Instruction
references also distinguish \code{frndint}, which can set denormal-operand,
from \code{fistp} and \code{fstp}, which do not.  The probe now treats this bit
as opcode- and priority-specific, tests five store/round/conversion boundaries
under nearest-even and toward-zero, and records exception-coverage counts.  The
result strengthened the executable oracle while reinforcing that floating
point must be modeled as an instruction/state machine rather than as pure real
arithmetic plus a single rounding function.

Future changes to the central claim or state boundary should be appended here
with the evidence that motivated them.
